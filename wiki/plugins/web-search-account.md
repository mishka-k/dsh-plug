# web-search-account — поиск по токену аккаунта

## 1 Зачем

Штатный `web-search-deepseek` берёт токен аккаунта только когда модель текущего хода пришла из
провайдера `deepseek-account`; на любом другом маршруте он молча уходит на `DEEPSEEK_API_KEY`
(разбор — страница «Авторизация веб-поиска» в каталоге знаний харнесса, вне этого репозитория). В профиле, где модели идут через `opencode-go`, это значит: аккаунт
подписан, токен живой, а поиск отвечает `401` ключом, который к аккаунту отношения не имеет.

Плагин добавляет второй провайдер — `deepseek-account`, который всегда шлёт токен аккаунта и
модель не спрашивает вовсе.

## 2 Как устроено

| Что | Как |
|---|---|
| Выбор | `web.searchProvider: deepseek-account` в патче профиля; установка бандла сама по себе ничего не меняет |
| Авторизация | `ctx.get('deepseekAccount').resolveToken(endpoint)` → заголовок `x-dsh-auth-token` |
| Запрос | POST `${baseURL}/messages`, Anthropic Messages + серверный инструмент `web_search_20250305` |
| Ответ | блоки `web_search_tool_result`, выдержки — из цитат текстовых блоков, дедуп по url |
| Токен | разрешается на каждый запрос, поэтому повторный вход действует без рестарта |

Код провайдера — копия логики штатного пакета с одним изменением: нет проверки модели. Протокол не
изобретался.

## 3 Проверка (29.10.2026)

| Что | Чем | Результат |
|---|---|---|
| токен аккаунта принимается эндпоинтом | прямой POST `api.deepseek.com/anthropic/v1/messages` с `x-dsh-auth-token` | `HTTP 200` |
| тот же токен как API-ключ | `Authorization: Bearer` и `x-api-key` | `HTTP 401` — подтверждает, что путь только через заголовок аккаунта |
| значение в сторе под `DEEPSEEK_API_KEY` на момент разбора | разбор формы | 36 знаков, UUID — tracking id app-managed ключа платформы, а не секрет; как ключ отбивается 401. Позже в стор положен настоящий `sk-…`, и штатный провайдер снова работает на любой модели |
| поиск через новый провайдер | `web_search` после смены `searchProvider` | вернул источники |
| поиск на модели не из аккаунта | субагент на `opencode-go/deepseek-v4.1-flash` вызвал `web_search` | `ok`, 8 источников — провайдер модель не спрашивает |

## 4 Подводные камни

- `x-dsh-auth-token` принимает только токен аккаунта; `Bearer`/`x-api-key` с тем же значением
  отбиваются, поэтому «подставить токен как apiKey» не работает.
- Переопределение строки `web` заменяет конфиг целиком: без `fetchProvider` загрузка страниц
  останется без провайдера.
- Провайдер отдаёт только поиск; чтение URL — отдельный провайдер (`web-fetch-http`).
- Если аккаунт отписан, инструмент честно скажет «нужен вход в аккаунт», а не покажет 401 от ключа.
